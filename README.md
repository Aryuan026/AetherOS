> 自己的实现方式，相邻重复的低信息消息不会反复叠加同一段提示。主动来信也会让消息

> 运行时只对这一类明确的过期资源错误生效：先以 `no-store` 核对服务器确有不同 build，
> 再做一次带版本身份的壳换页；普通 API 断网或模型请求失败不会触发。恢复过程不清理
> localStorage、IndexedDB 或 CacheStorage，也不会改动聊天、角色和记忆。发布端同时保留
> 相邻版本的哈希资源，照顾还没有运行过自愈代码的旧桌面壳。

> **2026-08-09｜聊天接续与长上下文整理。** Chat 不再只按固定条数截掉前文：达到
> 玩家设置的整理上限，或本机估算当前输入已经偏长时，会保留最近 10 个完整对话轮次
> 原文，把更早的实时聊天整理成一张可重建的“接续便签”。一轮中的多条角色气泡会一起
> 保留；编辑、删除、恢复或移动早期消息后，旧便签会按原始记录失效并重建。整理失败只
> 回退到原有的有限消息尾巴，不删除聊天，也不会把便签冒充长期记忆、当前心情、剧情
> 事实或行为要求。见面、电话、隐藏系统日志和旧日迁入尾巴不会被揉进 Chat 便签；电话、
> 主动来信、见面、主线、IF 与小场景的独立接续位置已经固定在代码契约中，运行时仍按
> 各自 App 分阶段接入。当前还没有宣称 provider prompt cache 已接通。

## 这是什么？

**AetherOS** 是一个装在你浏览器里的虚拟手机系统。

不是那种普通的聊天机器人——这里面有**桌面**、**APP**、**消息通知**、**相册**、**甚至电话功能**。你可以创造角色，给他们装进去，然后像真用手机一样跟他们互动。

本部署版默认内置的是维护者准备的示例角色，方便朋友打开就能聊天；内置角色的核心提示词默认隐藏，避免不熟悉角色卡的人误改。

### 酒馆角色卡与世界书导入

- `通讯录 -> 导入角色卡` 支持 AetherOS JSON，以及 SillyTavern V2/V3
  角色卡 JSON / 带 `chara` 或 `ccv3` 数据块的原始 PNG。角色卡内嵌世界书会
  一起进入以角色名字命名的专属分组：原文件启用的条目随整组启用，原文件停用的
  条目保留在归档中，不会被偷偷启用。
- `世界书 -> 导入资料` 支持 AetherOS JSON、SillyTavern 独立世界书 JSON、带内嵌
  世界书的角色卡 JSON / PNG，以及普通 TXT。选定角色归属后会直接识别并原子写入
  一个以来源命名的新分组，不再先翻一页很长的只读预览；无法解析时保持零写入。
  世界书卡片会直接显示正在使用它的角色姓名，而不只显示人数。
- `世界书 -> 添加` 只处理自己的创作：可以手写一条，也可以把素材交给系统主持 AI
  整理成一条或一组，结果仍要由玩家编辑确认后才保存。新建自定义分组也留在这条
  手写/整理流程里，不再作为首页上的空操作。自定义分组可以置顶和拖动排序；内置
  世界书也可以置顶或仅从资料库界面隐藏，两者都不会删除资料或改变已经启用的运行规则。
  角色专属组和具名通用组都可以整组归档：组内条目保留版本，空分组则直接从书架移除，同时
  清掉角色对该组的旧启用关系。归档页仍按原分组收拢；“恢复整组”会一次恢复该组
  当前归档的全部条目并重建原分组，但不会擅自重新启用给角色。确认不再需要后，
  归档页也能彻底删除单条或整组；这会连同历史版本一起清除，操作前会再次确认。
- `待归组`不是记忆，而是早期导入或旧版本留下、尚无正式分组归属的世界书。它们
  默认不参与角色运行，可以整批归入角色分组或“通用资料”下的具名分组，也可以整批归档。
- 自建世界书不允许跨角色借用单条。想把 A 的写法用于 B，需要复制到 B 的分组，
  复制品之后独立修改；古代背景、现代背景、城市资料等确实共享的内容，可以分别建成
  “通用资料”下的具名整组，并为每组选择一个或多个使用角色。导入时选错角色后也能
  整组改归属，不需要重新导入。
  删除角色会归档该角色的专属条目并删除其分组定义，但不会删除通用资料或已经
  复制到其他角色名下的独立副本。
- 普通 PNG 图片不等于 PNG 角色卡。文件里没有酒馆元数据时，页面会明确提示
  “只有图片”，可以另作头像使用，但不会凭图片猜角色设定。
- 第一条消息、备选开场和酒馆正则脚本暂不自动写进角色设定或执行。它们需要各自
  明确的运行位置，当前导入会如实提示数量，避免把开场台词固化成人设规则，或让
  外部脚本在不知情时生效。

### 纯小说与世界书递送

- `笔友会 -> 新建书稿` 默认使用“纯小说”。玩家写的是本轮续写要求，不会被保存成
  小说正文；模型产出的自然段落才进入手稿。切回“角色共创”后，原有角色执笔、点评
  和讨论仍然保留。
- 纯小说可以不选角色，直接使用本书补充设定；选定角色后，则从该角色已启用的
  世界书里按本轮话题、知情范围和字数预算取少量相关资料。这里不会把角色的聊天
  口吻或恋爱关系身份强塞进小说。
- 小说正文成功保存以后，系统才记录这次世界书递送回执。模型失败、空输出或正文
  未落库时不会伪造“已经使用过”的记录；普通角色共创与世界主持的知情范围也不会
  因为共用一个资料库而混在一起。

## 三种顶部外观与虚拟城区

`外观 → 界面外观 → 顶部样式` 提供三种可随时切换的样子：`经典手机` 恢复原来的现实
时间、Wi-Fi 与电量状态栏；`纯软件界面` 完整收回顶部信息带；`虚拟城区`
显示当前关系世界里的地点、时间与天气。纯软件仍是新配置的默认值，但旧版
明确显示状态栏的外观会迁回经典手机，不会被悄悄改掉。

经典手机只影响显示；纯软件只影响壳层留白。虚拟城区的地点、世界纪年、IANA
时区或固定 UTC 偏移、年份偏移和手动 / 本地季节天气，则只保存在当前浏览器的
面具 × 进度套组作用域里。三种模式都不会改写聊天消息、旧日迁入、对话日历或
备份里的真实时间，也不会自动生成剧情、任务或记忆。

外观页按使用顺序分成 `界面外观 / 应用图标 / 美化预设`。界面外观里先处理
`屏幕观感`，再进入壁纸、小组件与装饰组成的 `桌面布置`；经典手机本身就是
完整选项名，不再叠加“原样”角标。

`外观 → 应用图标 → 桌面布局` 可以隐藏、恢复和调整 App 顺序，Dock 也能单独
排序；App 分页按每页 8 个直接预览，跨过页尾就进入下一页，固定日历页不参与
排序。隐藏只影响桌面投影，不会卸载 App 或删除数据。`设置` 永远保留在 Dock，
并提供独立的“恢复默认布局”入口，避免把外观管理本身藏起来后无法找回。桌面
布局随美化预设与
整机备份一起往返；页面、布局与图标编辑器都从 `INSTALLED_APPS` 注册表投影，
新 App 注册后会自动补进桌面与美化入口。

角色卡与通讯录是管理区，所有角色都可以在这里查看和重新链接；聊天、群聊、
电话、见面、朋友圈、房间、日记、书房、时光簿、同行计划与剧情协作属于当前
面具的生活区，只读取已经链接的角色。没有链接时页面会停在明确空态，不会
为了填满界面而把系统第一位角色或未进入生活圈的角色偷偷拉进来。

## 旧日迁入与对话日历

这一轮给 AetherOS 补上了完整的历史记录入口，不再把“导入”藏在聊天页或工程演练里：

- `旧日迁入` 是独立 App，支持 TXT 和 Word（`.docx`）。可以先选择现有角色/面具，也可以使用空占位，完成后再生成对应关系。
- 已覆盖常见的 `user:` / `assistant:` / `char:` 加 `timestamp:` 导出格式；即使多个回合挤在 Word 的同一个段落里，也会按明确角色标记重新拆开。WPS / Word 把同一回合包成多个正文段落时，会一直收拢到真正的 `timestamp:`，正文里的“朋友圈 2025.8.29”不会再被误拆成另一条或错误日期。空段落和孤立时间行直接忽略，非空但没有可靠导出通道标记的内容完整保留为“原文片段”。这里的 `user` 与 `assistant/char` 只表示导出通道，不声称台词中的世界内说话者是谁。
- 文件在当前设备的浏览器里解析并写入 IndexedDB，不上传历史原文，也不借用部署服务器处理。单文件上限 64 MiB、最多 100,000 个文本单元；特别大的文件更适合在电脑网页版导入。
- `旧日迁入` 可以反复打开：同一组面具 × 角色能够分多轮追加不同文件，不同关系分别归档；同一文件重复选择时只去重，不会覆盖旧批次或强制跳回聊天。去重身份只看关系范围与源文件字节指纹，因此解析器升级后重新选择同一文件也不会生成第二份。
- 导入阶段只做关系归属、文件解析和本机原文归档，不要求新人逐条认领说话人，也不要求先区分“陪伴 / 剧情”或解释时间戳；重复原文也不会在入口被擅自合并。来源时间按原样保存，不在传输层换算异次元时间。
- 本机迁入工作区会分块落盘，刷新后可以继续；正式归档再按日期切成稳定的小块，不要求把一天几千条消息同时塞进页面。当前采用干净的 v3 日档仓，不读取或迁移朋友实测前的旧日档校对数据。
- `对话日历` 按当前角色 × 面具关系查看记录。打开某一天后使用全屏阅读器和分页窗口，人类可见的当天总条数不设业务上限。日档内可长按气泡或点整理按钮，批量合并、改说话人、归入正确日期、修改原文或删除；“原文片段”和未标日期记录也能校正，不必回到导入入口做题。
- 未标日期记录的“合并并归入日期”是一笔原子写入：目标日完整保存后旧位置才会一起收起，完成后页面直接跳到目标日期和合并结果。普通日期移动也会跟随跳转，不再让记录看起来凭空消失。
- 每一天都可以补录一条或多条缺失原文。补录先是可编辑草稿；`锁定当天`会确认整天并把其中的补录晋升为明确的人工历史来源。解锁后可以继续校正，补录也会退回草稿。人工校正仍使用高版本修订和旧位置 tombstone，原始 Word/TXT 从不被反写。
- 锁定只提高这一天作为历史来源的可信度。它不会把旧事变成当前情绪、当前生活状态、现实结论或已经发生的剧情；未来记忆后台也只能通过明确的“已确认补录”选择器读取这条通道。
- 对话可以剪藏为保留原文与来源的素材；剪藏不会自动改写人设、关系、记忆卡或提示词。
- 剪藏库顶部可以检索当前关系的全部本地聊天，包括原文片段。结果显示日期、导出通道与关键词高亮；没有通道的内容明确标成“原文片段”，不会冒充用户；点击会回到原始消息。当前是明确的关键词检索，语义/向量召回仍是后续升级位。
- 导入完成后可以从聊天页继续聊。第一次**成功**续聊会携带最近 24 条用户/角色历史消息；如果请求中断可以重试，成功回复落库后便不再每轮重复携带。完整档案仍可浏览，不会因为导入成功就全部塞进模型上下文；实际输入量会影响所选 API 的 token 费用。
- 这 24 条会明确标为“旧日档案”：主聊天模型可以读它们来接住关系，但当前近况、未完约定、关怀线索、Story signal 和情绪 Buff 只看实时消息。旧史不会单独推进角色生活状态、剧情收据或记忆写入。
- 历史原文是媒介中立的证据。`对话`只投影为过去档案，并明确当前仍是远程文字聊天；`见面`不会自动读取历史尾巴，也不会把旧动作、神态和场景当作正在发生。
- 对话日历已开放第一阶段的“旧日角色素材整理”：玩家选择全部记录或跨月日期范围后，会先看到消息量、token 与 API 调用估算；开始后，选定范围的原文片段会临时发送给当前已启用 API，分批提炼并由同一个模型做有硬预算的第二遍证据核对。默认回执诚实标记为 `same_model_second_pass`，不会靠改调用名字冒充独立评审。发布结果只保留非逐字的语言指纹、稳定细节，以及受 surface 限制的开场/场景候选；本机素材库不保存原句。API 失败、格式不完整或没有可靠发现时不会向聊天发布半成品；玩家后续修改、删除或补录来源日档，旧结果会立即失效，等待重新分析。它不会直接修改角色卡、当前心情、未完约定、Character Life、已游玩剧情或工具权限。
- 已复核或由历史分析 pass 发布的非逐字角色素材，可以在普通 Chat 中按当前相关性稀疏递送：低信号最多取一条合法声音底色，普通轮次也只使用一条真正相关的可选回应方向；关怀、边界、修复与生活细节都必须命中更具体的现场证据。选择器使用本地信号、中文 n-gram、近期回执轮换和多样性约束，不要求设备先做向量化。未来 embedding 只作为可重建的可选排序旁路，不能绕过面具/角色/世界线 scope，也不能把素材写成当前动机、工具权限或剧情事实。
- 每条新的一对一消息会在创建时固化角色、面具和进度套组归属。切换面具后再编辑、删除、清空，或等待较慢的 AI 回复落库，日档仍只回写到消息原来的关系；没有归属信息的旧消息会停止自动归档，避免误写到当前面具。

如果手机在大文件解析时内存不足，可以在电脑打开同一个网页完成导入。不过浏览器本地数据不会自动跨设备出现；电脑到手机的迁移仍应通过完整备份/恢复链完成，而不是偷偷上传聊天原文。

## 配置说明（怎么让角色说话）

打开应用 → 底部 Dock 的「设置」→ 填入你的 API 信息：

| 字段 | 说明 |
|------|------|
| **Base URL** | OpenAI 格式的 API 地址，如 `https://api.openai.com/v1` |
| **API Key** | 你的密钥，别告诉别人 |
| **Model** | 模型名，如 `gpt-4o-mini`、`claude-3-sonnet`、`deepseek-chat` |

**MiniMax TTS（可选）**：想在「电话」里用语音功能，需要在设置里填 MiniMax 的 API Key 和 Group ID。不然你就只能看文字，听不到我性感的声音。

> 也可以建 `.env.local` 文件预填默认值，但设置里的优先级更高。

### 现实同频感知

设置 → 实时感知里可以选择角色如何理解现实世界信号：

- **现实锚定**：真实日期、昼夜和天气会进入规则层；角色可以关心用户现实里的作息与天气，但不能声称自己能现实接送或物理介入。
- **昼夜同频**：不把真实日期当剧情日期，只共享昼夜节律与天气氛围，适合“同一世界不同地点”的日常陪伴。
- **剧情自由**：不使用现实时间和天气约束剧情，适合半夜跑白天剧情或完全沉浸世界线。

天气感知仍然依赖 OpenWeatherMap API Key。AetherOS 会记录短期天气变化，只在天气类型或温度明显变化时把它作为一次“悬挂线索”递给 AI，避免每轮都变成天气播报。

## 数据存储在哪？（你的秘密安全吗）

**主要存在你本地浏览器里**（IndexedDB）。

- 聊天记录 ✅ 本地
- 角色设定 ✅ 本地  
- 上传的图片 ✅ 本地
- 你的世界书 ✅ 本地

**当前没有自动云端备份**：
- 部署服务器只提供网页代码，不保存或辅助解析历史聊天原文
- 仓库里的可选云端依赖不代表聊天记录已经开启同步
- 换浏览器、清理站点数据或更换设备，都不会自动找回原设备的 IndexedDB

建议定期使用「设置」里的完整导出保存副本。跨设备迁移应当走用户主动持有的备份/恢复流程；在这条链路正式封箱前，不要把浏览器缓存当成唯一副本。

## 常见问题

**Q: 为什么角色不回我消息？**  
A: 检查 API Key、模型名称和网络连接是否可用。

**Q: 语音通话没声音？**  
A: 检查 MiniMax API Key、浏览器音频权限和设备音量。

**Q: 能部署到服务器吗？**  
A: 能。`npm run build` 出来的 `dist` 文件夹丢到任何静态托管就行。Vercel、Netlify、GitHub Pages，随便。但记住：数据还是存在用户本地，不是服务器上。

**Q: 怎么替换内置示例角色？**
A: 在 `context/OSContext.tsx` 里维护 `defaultBuiltInCharacters`。内置角色会被标记为 `isBuiltIn`，并通过 `lockPromptEditing` 隐藏提示词编辑位。

## 给想二改的人（开发者区域）

如果你想在这个基础上加功能，先看这几句话：

### 稳定记忆、前台接续和来源证据分开，别把所有东西都塞进 ContextBuilder

**基础角色上下文**（人设、精炼记忆、关系印象、角色世界观）通过
`ContextBuilder.buildCanonicalCoreContext()` 组装。它不再把挂载世界书整本塞进
已迁移入口；Chat/Call 另行使用带关系 scope、知情范围、相关性和预算的 typed
Worldbook projection。尚未迁移的 App 暂时走命名明确的兼容 wrapper，而且只允许
明确公开且全局的资料进入。稳定角色底板包含：

- 角色基础设定（systemPrompt + worldview）
- 用户档案（你的名字、人设、关系标签）
- 精炼的月度记忆摘要
- 角色对你的关系印象（MBTI分析、喜好、情绪波动）

挂载的世界书正文不属于这块稳定底板。自建世界书由角色的整组 ID 提供候选，内置
资料继续由代码管理；Chat/Call 从当前
canonical library revision 挑选本轮真正相关的少量资料。普通“你好 / 嗯 / 在吗”不
带明确引用时不会注入世界书，也不会留下递送回执。

**前台聊天接续** 走 `domain/conversationContinuity/` 与
`utils/conversationContinuity.ts`。Chat 始终保留最近 10 个完整用户轮次原文；更早的
实时消息只在达到玩家设置的整理上限或估算输入超过 12,000 token 时，增量折成当前关系
专属的可重建便签。便签仍与正常 message history 一起进入 API 请求，但不是长期记忆，
不能写 Character Life、Narrative、提醒或关系结论。具体跨 App 插槽见
`docs/CONVERSATION_CONTINUITY_CONTRACT.md`。

**Provider Prompt Cache** 仍是后续成本优化，不是当前已启用功能。稳定/动态分层、
供应商能力边界、App 独立 cache lane 与真实命中验收规则已经记录在
`docs/PROMPT_CACHE_PLAN.md`；普通 OpenAI 兼容接口不会被擅自塞入 Anthropic 的
`cache_control` 字段。

**聊天回复格式** 走关系作用域的本机资产。默认的 `跟随玩家格式` 只参考玩家当前消息使用的是纯对白、括号动作、叙述混合还是自然段落，再让角色按自己的口吻使用相应文本结构自然分段；它不模仿玩家的语气、措辞、句式、节奏或口癖，也不覆盖角色卡。页面会把这次普通文本回复完整保留为一个气泡。`只发消息` 则启用严格远程 IM 约束，模型用换行标出独立消息，页面再拆成多条气泡。表情包、语音等真实 App 动作仍各自保存为独立消息；主动来信始终使用消息体。

全新安装与没有聊天装扮字段的旧本机数据默认使用 `简约` 聊天主题；已经明确保存过 `深空 / 简约 / 微信 / 自定义` 的选择不会被新建或迁入角色覆盖。

**世界线交汇记忆** 走 `utils/memoryCore/`。它把聊天、见面、主动来信、时光簿、角色记忆、未来原作剧情/约会分支理解成同一段关系里的不同入口，按需挑一小段上下文递送给模型。

**记忆候选整理** 也放在 `utils/memoryCore/`，但它和递送、最终写入不是一回事。Chat、见面和旧日来源先变成带完整关系 scope 与 revision 的 `InteractionEvidence`；`autoMemory` 只提出可追溯的时光簿候选，`memoryDm` 使用同一个前台聊天 API，在配置的 20-100 轮对话后生成版本化 interpretation pass 与 extraction receipt。当前盒明确是 extraction-only：不会直接改写 `char.memories`、时光簿、提醒、剧情或 Character Life；后续必须经过独立 Memory Promotion / Narrative / Life 写权门。

这意味着：不是“只要存进 IndexedDB 就自动进 Prompt”。新功能如果想成为可回忆内容，应该接入 memoryCore selector，标明来源、世界线范围、知情范围和状态，再由具体入口按预算选择。

### 想加新 App？

1. 在 `apps/` 里新建一个 `YourApp.tsx`
2. 在 `types.ts` 的 `AppID` 枚举里加个 ID
3. 在 `constants.tsx` 的 `INSTALLED_APPS` 数组里注册（图标、名字、颜色）
4. 在 `App.tsx` 的 `renderApp()` 里加 case
5. 完事。UI 风格参考现有的用 Tailwind + glassmorphism。

### 数据流

```
用户操作 → OSContext（全局状态）→ IndexedDB（持久化）
                    ↓
              Chat/App 组件读取
                    ↓
        ContextBuilder + memoryCore 组装 Prompt
                    ↓
              调用 LLM API
```

所有数据都是 **local-first**，没有后端服务器这个概念（除了那个可选的云端备份）。
